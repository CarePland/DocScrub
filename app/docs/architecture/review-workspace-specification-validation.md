# Review Workspace Specification — Validation Against Andrew's Notes

**Source of observations:** `DocScrube-20260728-AG-notes.docx` — informal notes recorded while comparing the original Python reviewer application to the current browser implementation, including 9 embedded screenshots (Python UI and current build).

**Compared against:** `docs/architecture/review-workspace-specification.md` (the "Review Workspace Specification").

**Method:** the notes doc mixes several distinct claims per paragraph in places. Each is atomized into a single observation below so it gets its own classification, rather than letting a compound paragraph hide a partial gap. Screenshots are cited by content (e.g., "Group Check, Python") since the notes doc doesn't caption them.

This is a design review, not an implementation change. The specification was not modified.

## 1. Items already represented in the specification

Checkbox multi-select with "select all" (#4), the Space-bar detail-panel toggle (#5), color-coded top-level confidence (#9), Not Quite's per-member inspection model (#19), the Redaction Rules panel's deliberate non-Python placement (#21), the Candidate Detail Panel's overall design and quality (#23), and Expert View's design and quality (#25) are all already captured, matching or closely matching what the notes describe. Several others (#18, #20, #22, #24) name a gap the specification already partially acknowledges but describes at lower fidelity than the notes now provide — these are listed above as "Already captured" or "Implied but incomplete" depending on how precisely the existing text matches, with a specific suggested addition in each case.

## 2. Items that should be added to the specification

These are documentation gaps, not necessarily implementation gaps — behavior that may already be intentional but was never written down, or design constraints that should be stated as guarantees rather than left implicit:

- Count semantics on group/candidate rows (#3)
- A named guarantee that navigation is standardized across every reviewable area (#14)
- "Efficient, compact, fast" as explicitly named target qualities, not just implied by "calm/low cognitive load" (#15)
- Visual-quietness (sizing/color/saturation restraint) as an explicit target, not just implied (#13)
- The Command Bar's legend varying by sub-state, not just by stage (#20)
- An explicit "stay broad, not granular" categorization constraint (#24)
- An explicit anti-pattern note against Python's list-header density (#22)
- The richer inline editor's radio-quick-pick detail (#18)

## 3. Items that should become future implementation work

These describe real behavior gaps between the current build and either Python or Andrew's stated preference — not just missing documentation:

- Two-column responsive layout for list panels (#1)
- Reduced/removed row boxing for density (#2)
- Domain-aware Tab/Shift+Tab traversal that preserves and advances expand/collapse state (#6), paired with a default-open state for the newly-focused item (#7)
- Resolving the "needs attention" pill — first needs a decision on what signal drives it, then implementation (#8)
- Reconciling the default sort order (frequency vs. confidence) — a decision, then a one-line code change (#10)
- Removing embedded keyboard shortcuts from button labels now that the Command Bar covers discoverability (#12)
- Adding Shift+Arrow category navigation to the already-built Category Check (#16)
- Deciding whether "navigate within an open item" via arrow keys should generalize beyond Not Quite (#17)

The group-level naming question (#11) is really a decision to make before it's implementation work — see below.

## 4. Recurring themes

**Terminology drift between what was decided and what got built.** #11 is the clearest instance: the notes state directly that "Flatten"/"Reject" were never agreed terms, yet they're now load-bearing vocabulary in both the specification and the shipped keyboard bindings. This is worth resolving deliberately rather than by inertia, since Feature 001's own documentation attributes the three-term vocabulary to "Andrew's instruction" — these notes suggest that account may not be quite right, or that the intent has since changed.

**A consistent preference for fewer visual signals, not more.** Rows without boxes (#2), buttons without embedded shortcuts (#12), broad rather than granular categories (#24), and an explicit call-out that Python's own list header felt cluttered (#22) all point the same direction: reduce the number of distinct visual elements competing for attention on screen at once, even where each element is individually well-designed. This is the same instinct the specification already names as Design Principle #6 ("favor clarity over quantity") — these notes give it several new, concrete instances to apply it to.

**Small interaction mechanics carry real weight.** The count-semantics clarification (#3), the "needs attention" pill (#8), and the specific Tab/Shift+Tab-preserves-state behavior (#6/#7) are all easy to treat as trivial, but each is exactly the kind of detail the notes' own framing warns against skipping — the difference between software that merely works and software that feels considered. None of these are large builds; all of them are currently either undocumented, unbuilt, or both.

**Navigation and discoverability are more contextually rich in Python than the current specification captures**, even though the specification's overall two-axis navigation model (§7.1) is structurally sound. The Category Check Shift+Arrow behavior (#16), the richer per-sub-state Command Bar legend (#20), and the still-open question of how far "navigate within an open item" generalizes (#17) are all instances of the same underlying pattern: Python's keyboard model had more contextual nuance than has been carried into either the specification or the implementation so far, and the specification should catch up to what's now confirmed (rather than the implementation being asked to guess at undocumented Python behavior later).
