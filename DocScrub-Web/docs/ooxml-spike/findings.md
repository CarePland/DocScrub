# OOXML structural spike — findings

Generated by `scripts/ooxml_structural_spike.py` against two documents
currently sitting in `work/pii_docx_redactor/.local_web_state/`: the most
recent real upload (`upload.docx`) and its redacted output (structurally
identical, as expected -- DocumentRebuilder-equivalent processing preserves
paragraph/run/table structure), plus the trivial `synthetic_transcript.docx`
used for domain-parity fixtures, included for contrast.

Raw numbers: `structural-findings.json`. No document text is reproduced here
or there.

The gap between these two rows is the whole point of running this spike
before finalizing browser parser/rebuilder contracts: the synthetic fixture
the domain-parity pipeline currently exercises (§13.1) is structurally
trivial (one run per paragraph, no fields, no drawings) and would not have
surfaced any of the findings below. A real document does.

## Fidelity risks confirmed present (not hypothetical)

1. **Run-splitting is real and non-trivial.** 457 of 6,134 paragraphs (about
   7.5%) split their text across more than 3 `<w:r>` runs, with one paragraph
   reaching 15 runs. This directly confirms the risk architecture v0.2 §15.2
   already named ("Text split across Word runs can make replacements
   difficult") -- it is not a theoretical edge case for this document set,
   it is routine. Any replacement logic that assumes a candidate's text lives
   in one run will miss real occurrences in Teams-transcript-style exports.

2. **Complex field codes are heavily used (1,533 occurrences).** Word field
   codes (`w:fldChar`, paired with `w:instrText`) do not put their resolved
   text in an ordinary `w:t` node the same way plain text does. A
   DocumentParser that only reads `w:t` nodes -- which is the simplest and
   most likely first implementation -- risks silently missing candidate text
   that lives inside field results (e.g. cross-references, TOC entries, or
   Teams-export metadata fields). This needs an explicit decision in Phase 2:
   either resolve field text into the DocumentModel as ordinary content
   blocks, or explicitly flag field-derived text as an unsupported/warned
   region rather than silently skipping it.

3. **Drawing objects and legacy pictures are present in volume (530 + 73).**
   These commonly hold text boxes with independent text runs not reachable
   via ordinary paragraph traversal -- the existing README already flags this
   ("text boxes... may not be redacted perfectly in this MVP"). This spike
   confirms the volume is not negligible for a real document of this kind
   (Teams transcript exports appear to embed a meaningful number of these,
   plausibly from pasted screenshots, embedded meeting artifacts, or
   Teams-specific export formatting).

4. **Nested tables exist (depth 2), consistent with the current app's stated
   support** ("Tables, including nested tables where python-docx exposes
   them"). Any browser-side traversal needs to handle at least this depth,
   not just single-level tables.

5. **No tracked changes, comments, footnotes, or endnotes** were present in
   this document. That does not mean DocumentParser can skip handling them --
   it means this particular spike sample doesn't exercise that path. §15.4's
   open question ("Which unsupported Word constructs block export versus
   generate warnings?") still needs a source document that actually has
   tracked changes/comments before it can be answered with evidence rather
   than assumption.

## What this does and does not prove

This confirms *what* the browser parser/rebuilder will have to handle for at
least one real, representative document -- it does not confirm that a
browser JS OOXML library can handle it with acceptable fidelity. That is the
actual Phase 2 spike (architecture v0.2 §14), and it requires a real
npm-installed library (candidates to evaluate: `docx`, `mammoth` for reading,
possibly a lower-level ZIP+XML approach mirroring this Python script's
technique but in JS) on a machine with normal network access, which this
environment does not have.

## Recommended next steps for the Phase 2 spike

1. Pick 2-3 real (de-identified) documents spanning the range seen here --
   at minimum one with run-splitting >7 in a paragraph, one with drawing
   objects, one with complex fields -- as the actual Phase 2 acceptance
   fixtures, rather than starting from a synthetic document.
2. Decide field-code handling (resolve into DocumentModel vs. explicit
   unsupported-feature flag) before committing to DocumentModel's shape --
   this affects §6.2's "supported and unsupported feature indicators" schema
   directly.
3. Confirm whether any candidate documents in real use have tracked changes
   or comments; if none currently do, treat §15.4's tracked-changes question
   as lower priority than field-code and drawing-object handling, which this
   spike shows are the actually-occurring risks.
4. Re-run `scripts/ooxml_structural_spike.py` (extend its `candidates` list)
   against any new documents added to the fixture corpus, so structural
   coverage is tracked deliberately rather than by accident.
